# API 设计规则

本文只定义长期有效的 API 设计原则。具体路径、字段、枚举和响应结构以 `docs/api/openapi.json` 为唯一权威契约，不在本文维护接口清单副本。

## 1. Contract First

公共 API 变更必须按以下顺序执行：

```text
更新 OpenAPI
  → 生成并校验前端类型与 Client
  → 实现后端
  → 更新前端调用
  → 执行契约与兼容验证
```

不得先修改实现，再以文档追认；不得通过前端兼容逻辑掩盖契约不一致。

## 2. 资源与路径

- 公共接口统一位于 `/api/v1`。
- 路径使用复数资源名和 kebab-case。
- 路径参数必须表达明确对象类型，例如 `clanId`、`branchId`、`personId`。
- 复杂业务动作使用可识别的动作子资源，不使用含义模糊的 `/do`、`/handle`、`/process`。
- 列表、详情、创建、修改和删除语义保持一致。

## 3. 请求与响应

- API DTO 与数据库实体、领域实体分离。
- 请求对象只包含客户端可提交字段；后端计算字段、权限结果和审核状态不得由客户端伪造。
- 响应使用稳定业务字段，不向普通用户暴露无必要的技术 ID、内部表名或堆栈信息。
- 时间字段使用明确格式和时区语义；面向用户的时间遵循 `docs/governance/time-and-timezone.md`。
- 金额、数量、布尔、枚举和日期不得通过含义不明的字符串传递。

## 4. 分页、排序与搜索

所有可能增长的集合必须具有分页、游标、硬上限或明确批次限制。

分页响应至少表达：

```text
items
pageNo
pageSize
totalElements
```

- 排序字段必须受控，稳定排序以唯一字段收尾。
- 搜索参数需要明确最小长度、默认值和组合约束。
- 总数、分页和过滤必须在权限范围生效后计算。
- 不返回无边界全量宗族、人物、关系或图谱数据。

## 5. 错误与状态

- 错误码稳定、可定位、可被前端分类处理。
- 区分参数错误、业务冲突、无权限、资源不存在、并发冲突和系统异常。
- 不返回敏感内部信息、SQL、文件路径或堆栈。
- HTTP 状态、业务错误码和消息语义必须一致。
- 幂等、重复提交和并发更新需要明确处理方式。

## 6. 权限、隐私与审核

- 后端是权限和隐私结果的唯一可信来源。
- 对象级操作能力应通过明确字段或动作集合返回，不要求前端根据角色名猜测。
- 在世人员、来源附件、导出和审核数据遵循最小披露。
- 人物、关系和来源绑定等正式数据变更不得绕过审核闭环。
- 无权限响应不得泄露目标对象是否存在、名称、数量或摘要。

## 7. 兼容与废弃

破坏性变更前必须说明：

- 影响的调用方；
- 兼容窗口；
- 新旧字段或枚举映射；
- 数据迁移方式；
- 废弃和删除条件；
- 回滚或前向补偿方案。

旧字段只在明确兼容期内保留，不形成永久双契约。

## 8. 验证

API 变更至少执行：

```bash
cd frontend/genealogy-web
npm run api:generate
npm run api:check
npm run typecheck
```

并执行相关后端 Controller、Application、权限和契约测试。OpenAPI 与生成产物不一致时，任务不得标记完成。

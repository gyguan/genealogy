# Issue #870 大规模并发与容量压测方案

## 目标

建立可重复执行的容量测试基线，覆盖读多写少、读写混合、世系查询、阶梯加压、峰值突发和持续负载，并输出响应时间、吞吐、错误率、资源利用率、数据一致性和扩容建议。

## 环境与结论边界

PR 默认使用 GitHub-hosted Ubuntu Runner、PostgreSQL 16 和单个 Java 17 JVM（最大堆 1 GiB），用于验证脚本、阈值、瓶颈定位和工程容量基线。该结果不等同于生产集群容量。

生产等价环境通过 `workflow_dispatch` 选择：

- `ci`：5 → 10 → 20 → 30 → 50 VU，覆盖基线、阶梯、突发和短持续负载；
- `capacity`：25 → 50 → 100 → 200 → 400 VU，并在 200 VU 持续 5 分钟；
- `soak`：默认 50 VU 持续 30 分钟，可配置时长和 VU。

## 业务负载模型

- 35% 人物分页查询；
- 20% 宗族详情查询；
- 15% 支派查询；
- 25% 正式世系查询；
- 5% 人物草稿创建。

每个虚拟用户独立登录，使用真实 Session Cookie 和 CSRF Token。写请求使用唯一 `personCode`，测试后检查重复、部分正式数据和数据库死锁。

## 门禁阈值

- HTTP 错误率 < 1%；
- HTTP P95 < 1500 ms，P99 < 3000 ms；
- 世系查询 P95 < 2000 ms，P99 < 4000 ms；
- 通用检查和写操作成功率 > 99%；
- 静默业务失败、重复编码、意外正式数据、OOM、不可恢复线程阻塞和数据库死锁为 0。

## 监控与 Artifact

每 2 秒采集：

- 后端进程 CPU 与 RSS；
- PostgreSQL 连接数、事务提交/回滚、块读取/命中、临时文件和死锁；
- k6 P50/P95/P99、吞吐、错误率、检查成功率；
- 后端完整日志和数据一致性 SQL 结果。

Artifact 保留 `k6-summary.json`、资源 CSV、执行报告、种子数据清单、数据库一致性结果和后端日志。

## 容量与扩容触发条件

以下任一条件持续出现时，应在达到业务峰值前扩容或优化：

- P95/P99 超过门禁阈值；
- 错误率达到 1%；
- 数据库连接数达到连接池容量的 70%；
- CPU 持续达到 70%；
- RSS 持续增长且负载回落后不能恢复；
- 出现慢 SQL、临时文件突增、连接池等待或写操作失败。

## 数据清理

压测数据均带有 `#870 可清理容量压测` 标识或 `LOAD-` 人物编码前缀，可按测试宗族整体清理。正式世系基线仅用于当前隔离测试宗族，不影响业务宗族。

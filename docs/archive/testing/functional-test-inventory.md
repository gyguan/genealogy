## 4. 前端自动化资产

### 4.1 常规 Frontend CI 已覆盖

- Feedback、EmptyState、ConfirmAction 等 UI 治理契约；
- 多选查询、URL 状态和导航保护；
- 建谱向导状态、依赖、表单和完成判定；
- 人物编辑、详情、关键事件保存流；
- 世系图模型；
- 审核中心分页；
- 首页、修谱工作台、数据导入状态模型；
- TypeScript 与生产构建。

### 4.2 Playwright 已覆盖但主要使用 Mock 的场景

现有宗族文化等 Playwright 用例通过 `page.route('**/api/v1/**')` 模拟接口，可有效验证：

- 页面结构与可访问性；
- 查询条件和 URL 恢复；
- Drawer、编辑页面和移动端布局；
- 403 等前端反馈；
- 非活动 Tab 不发起请求。

但不能验证：

- 后端权限判断；
- PostgreSQL 数据是否真实写入；
- Flyway 和约束；
- 审核快照与正式数据原子生效；
- 前后端 DTO 是否在运行时一致；
- 文件下载、并发和事务失败。

## 5. CI 现状

### Backend CI

执行 `mvn -B -DskipITs package`，能完成编译、单元测试和打包，但明确跳过集成测试。

### Frontend CI

执行大量模型、契约、TypeScript 和构建检查，但未将 `npm run test:e2e` 作为全量常规门禁。

### 结论

当前 CI 擅长发现代码级和页面契约回退，尚不能证明核心业务在真实数据库环境中端到端可用。

## 6. 测试资产分类规则

后续所有用例和报告统一使用以下类型：

- `UNIT`：单类/单服务测试，外部依赖 Mock；
- `MODEL`：纯状态或算法模型测试；
- `CONTRACT`：OpenAPI、DTO、源码结构和治理契约；
- `UI_MOCK_E2E`：浏览器测试，但业务 API 使用 Mock；
- `DB_INTEGRATION`：真实 PostgreSQL、Flyway 和 Spring 容器；
- `REAL_E2E`：真实前端、后端和 PostgreSQL；
- `MANUAL`：仅适合人工验证的视觉或外部系统场景。
